# Migration — what carries over, and how

The children's progress lives in `localStorage` on each device and is mirrored to Firestore, key by key, by the family sync. The rebuild keeps **every key name and every value shape** of the old app, so the switch needs no data migration on any device and nothing in the cloud (DESIGN §11).

This document is the contract. The table below is generated from the registry in `app/core/storage.js` (`node tools/keys-table.mjs`); a test fails when the two differ.

## Rules

1. Existing keys keep their exact names and shapes. New data goes into new keys (`since v2` in the table).
2. `<P>` is a profile's storage name — the display name the old app had in its code. It comes from the device and the family sync at runtime; the code ships none. It never changes once created.
3. Every synced key has one merge strategy (`app/core/merges.js`), pinned by tests: idempotent, commutative, associative, and progress never goes down.
4. Spaced-repetition intervals per module are unchanged (quizzes `[0,1,2,4,7,14]`, nouns `[0,1,2,4,8,16,32,64,90]`), so no card becomes due earlier or later.
5. Question ids are frozen: the ids the old app generated from the question text are written into the content files once (`tests/fixtures/live-ids.json`, `tools/freeze-ids.mjs`) and a test keeps them equal.
6. Legacy, read-only keys are read for the first run (old editor overrides, old extra profiles, the old trainer's last profile) and never written again.

## Differences the children will not notice, written down anyway

- **Records gain optional fields.** SRS records may carry `lz` (a decaying leech score; old records start from `w`). The merge rules ignore unknown fields and pass them through.
- **Retry counts once.** The old quiz called the scheduler twice for "wrong, then right on the retry" (two drops). v2 applies one review per card per session (one drop).
- **Day boundary.** v2 computes the day in Europe/Berlin; the old app used UTC (which flipped at 01:00/02:00 German time). Existing `due` dates keep their strings; the difference is at most a day, once.
- **History dates.** The old app stored `D.M.YYYY` unpadded and sorted as if padded; v2 keeps writing the same format and sorts both forms correctly.
- **Lernpfad state** (`gram_path_<P>`) merges deep instead of flat, so units passed on two devices are both kept (DECISIONS 2026-10-18).
- **Old editor overrides** (`wq_editor_QB*`) no longer replace shipped content at runtime. Their differences are folded into the content files before the switch (from a backup export) and the keys are left alone.
- **Eltern** is a mode, not a profile. The old `wq_Eltern*` keys stay untouched and unused.

## Staging (`/next/`)

The staging shell sets a namespace: every key is written as `next_<key>`, so the new app can be tried on the real iPad with a *copy* of the device's data ("Daten von diesem Gerät kopieren") while the live app and the cloud stay untouched. The family code is never copied, and the sync refuses to run on a namespaced store. At the switch the namespace is empty and the real keys are used as they are.

## Rollback

The switch is one commit. Reverting it brings the old app back; the old app finds its keys unchanged (v2 only adds keys and optional fields it ignores).
